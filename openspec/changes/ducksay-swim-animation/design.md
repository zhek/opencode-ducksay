# Design

## Context

См. `proposal.md` — Why. Здесь только то, что определяет технический выбор.

Наблюдённые факты об API хоста, на которые опирается дизайн (проверены по типам `@opencode/plugin@2.0.28` и по исходникам `@opentui/core@0.6.4`):

- Слот `sidebar.content` передаёт в `render` реактивный `sessionID`; вход слота не содержит ширины (в отличие от `session.panel`, где есть `width`).
- `data.session.status(id)` отдаёт `"idle" | "running"`, но документация CLI-плагинов помечает реактивность только у `ui.model.current()` и `ui.tabs.list()`. Для `data.*` такой пометки нет.
- `storage.memory(key, { initial })` возвращает `Store<Value>` из `solid-js/store` — чтение его полей в вычислении Solid реактивно по определению; значение переживает hot-reload плагина и не переживает перезапуск TUI.
- `PluginOptions` — это `Record<string, any>`: хост не проверяет ни типы, ни диапазоны опций.
- Рендерер работает не постоянно, а по запросу: пока счётчик `liveRequestCounter` равен нулю, цикл кадров стоит. `requestAnimationFrame` внутри сам вызывает `requestLive()`, а после выполнения каждого колбэка — `dropLive()`, то есть цикл, перерегистрирующий себя в колбэке, держит и отпускает себя сам. `targetFps` по умолчанию 30.
- `renderer.clock` — тот же `Clock`, который принимает `CliRendererConfig`, поэтому `testRender` позволяет подставить `ManualClock` иAdvance время вручную.
- У `Renderable` есть геттер `width`, а у JSX-элементов — проп `ref`, поэтому ширину своей области можно измерить самому.
- Серверное событие `session.status` несёт `{ sessionID, status }`, где `SessionStatus` — это `idle`, `busy` или `retry`.

Текущий код: `src/duck.ts` (одна константа `DUCK` из трёх строк шириной 4, 8, 8), `src/tui.tsx` (компонент `Ducksay` как чистая функция пропсов + `Plugin.define`, регистрирующий `append: "sidebar.content"`). Существующие тесты рендерят раздел через `testRender` без хоста OpenCode и читают кадр через `captureCharFrame()`.

## Goals / Non-Goals

**Goals:**
- Утка перемещается по полосе панели весь ход сессии, разворачивается у краёв и останавливается у края носом к центру.
- Плагин читает скорость из опции, разбирает её значение по единым правилам и не падает на мусоре.
- Кадры рендерера занимаются только на время анимации и освобождаются во всех остальных состояниях.
- Поведение проверяется автоматическими тестами, а нарисованный вручную спрайт — дополнительно глазами в живом TUI.
- Раздел остаётся чистой функцией пропсов, чтобы его можно было тестировать без хоста.

**Non-Goals:**
- Новый слот, новая панель, другой раздел или другая его позиция: раздел `Ducksay` остаётся последним в `sidebar.content`.
- Отдельная настройка скорости для докировки: сегодня её нет, и появление второй опции должно быть аддитивным, а не заменой `swimSpeed`.
- След воды, звук, наклон утки, вертикальное покачивание, реакция на конкретные типы инструментов.
- Сохранение позиции утки между перезапусками: поза после запуска определена спецификацией и не зависит от прошлого.
- Настройки, зависящие от сессии или проекта: одна глобальная скорость, потому что `cli.json` — глобальный файл, и всё остальное в плагине тоже глобальное.
- Требования о заголовке, порядке разделов и непереносе строк арта не меняются.

## Decisions

### Момент старта и конца плавания — статус сессии

Плавание привязано к `session.status`: плаваем при `busy` и `retry`, стоим при `idle`.

Альтернативы: `session.text.delta` (только поток токенов) — отвергнута, утка замирала бы на время вызова инструмента и ожидания прав, и это читалось бы как зависание; `session.execution.started/succeeded` — покрывает ход, но не покрывает повторную попытку после ошибки авторизации; «окно от промпта до первого ответа» — хрупко и на глаз неотличимо от первого варианта.

`retry` считается занятостью намеренно: откат с бэкоффом — это ожидание, и утка должна показывать, что работа продолжается.

### События превращаются в состояние в store, а не читаются напрямую

`setup` подписывается на `session.status` и складывает занятость в `storage.memory { busy }`, а компонент читает `busy[sessionID]`.

Альтернатива: читать `data.session.status(sessionID)` прямо в рендерере. Отвергнута, потому что её реактивность не задокументирована, а `Store` из `storage.memory` реактивен по определению. При этом `data.session.status()` остаётся как значение по умолчанию на тот случай, если панель открыли посреди хода и ни одного события ещё не пришло.

События фильтруются по `sessionID`: они приходят по всем сессиям, и без фильтра утка панели дёргалась бы от фоновой вкладки. Сами события не привязаны к одной сессии и накапливаются в store по всем.

Позиция утки в store не хранится: поза после запуска задана спецификацией, а переживание hot-reload для анимации не нужно.

### Кадры — `requestAnimationFrame`, перерегистрирующий себя

Компонент в `onMount` регистрирует кадр, в колбэке считает прошедшее время, двигает утку и регистрирует следующий кадр; в `onCleanup` кадр отменяется. Отмена снимает `live`-счётчик, и цикл рендерера останавливается сам — вручную балансировать `requestLive`/`dropLive` не нужно.

Альтернативы: `setInterval` плюс `renderer.requestRender()` — отвергнута: таймеры не привязаны к кадрам рендерера, отмена требует отдельного аккуратного `clearInterval`, а кадры всё равно придётся запрашивать; `renderer.setFrameCallback()` — отвергнута принципиально: сеттер один, и вызов из плагина затёр бы колбэк самого хоста.

Часы не пробрасываются в компонент: `deltaTime` приходит из цикла рендерера, а тест подставляет `ManualClock` через конфиг `testRender`.

### Ширина полосы измеряется у себя

Полоса — ширина контейнера раздела, а предел положения — `max(0, ширина − ширина арта)`. Ширина читается у renderable, полученного через `ref` на корневой `<box>`, на каждом шаге.

Альтернатива: зашить константу `SESSION_SIDEBAR_WIDTH = 42` и производную от неё ширину 37. Отвергнута по причине, уже зафиксированной в прошлом change: это жёсткая связь плагина с внутренней константой чужого проекта, которая ломается при изменении раскладки. Проверка — `test/section.test.tsx` уже рендерит при ширине 42, то есть поведение на реальной ширине панели продолжает проверяться.

### Поза в покое выводится из инварианта «у края носом к центру»

Утка всегда смотрит в сторону движения, а засыпает сразу после разворота у края. Из этого следует всё остальное: старт — левый край носом вправо; докировка — до ближайшего края и разворот; чужая настройка «возвращаться в ноль» не понадобилась бы вовсе.

Альтернатива: после конца хода возвращать утку к левому краю — отвергнута: это второй, независимый способ завершения анимации, своя фаза и свои тесты, при выигрыше в одну колонку.

### Второй спрайт — зеркальное отражение первого, а не нарисованный отдельно

Нос вправо получается отражения исходного спрайта по горизонтали: строки разворачиваются, а глифы, у которых есть зеркальная пара, заменяются на неё — `<`↔`>`, `(`↔`)`, `/`↔`\`; остальные символы, включая пробелы, остаются как есть.

Простой разворота строк недостаточно: `<` переехал бы в конец строки, но раскрылся бы в ту же сторону, то есть клюв смотрел бы влево, и уточка получилась бы с хвостом слева и головой справа. Именно замена глифов превращает перестановку в отражение.

Исходные строки выравниваются по общей ширине блока до отражения. Без этого у отражения нет пары: строка `  __` длиной 4 не имеет соответствия, и «зеркало» перестаёт быть определённым. Ширина блока становится свойством арта, а не результатом подгонки, и предел положения перестаёт зависеть от конкретного глифа.

Альтернативы: нарисовать второй спрайт вручную и полагаться на глаз — отвергнута: результат похож на зеркало только приблизительно, а расхождение заметно именно в момент разворота, то есть в движении; зеркалировать на уровне ячеек — в OpenTUI недоступно; вычислять второй спрайт из первого в рантайме — отвергнута: арт остаётся данными, которые читаются и правятся как данные, а неизменность отношения обеспечивается тестом; держать в арте только нос вправо и разворачивать его — отвергнута тем же, что перевёрнутый нос влево смотрит вправо, то есть нужен всё равно исходный.

Отношение зеркала проверяется тестом: каждая строка правого спрайта равна развёрнутой строке левого с заменой парных глифов, а двойное отражение возвращает исходник. Тест не фиксирует сами символы и потому не мешает правке рисунка, но ловит правку одного спрайта в одиночку. Визуально результат проверяется отдельно — снятием кадра в tmux.

### Скорость измеряется колонками в секунду

Скорость переводится во время между колонками как `1000 / swimSpeed`, накопленное время сравнивается с этим шагом. Единица выбрана потому, что это единственная величина, которую видно глазом, и она не зависит ни от частоты кадров, ни от ширины панели.

Альтернатива: «колонок за фиксированный такт 80 мс» — отвергнута: число в конфиге оказывается привязанным к внутренней константе, которую нельзя поменять незаметно для пользователя; строковые режимы вроде `slow`/`fast` — отвергнуты: три состояния вместо числа, при этом точная настройка невозможна.

### Нулевая скорость выключает анимацию, а не её темп

`swimSpeed: 0` проходит мимо разбора как корректное значение и выключает анимацию: компонент не заводит цикл кадров вовсе, уточка стоит у левого края носом вправо. Это осмысленное значение, а не отключение плагина, потому что раздел с заголовком и уточкой остаётся на месте.

Нулевая скорость полностью воспроизводит поведение 1.0.0, включая его цену: без цикла кадров.

### Разбор значения — чистая функция с явной проверкой отсутствия

`resolveSwimSpeed(options)` живёт отдельно от компонента и возвращает число:

| вход | результат |
| --- | --- |
| опции или ключа нет, `null` | 12 |
| строка, у которой `trim()` пуст | 12 |
| строка с числом | это число |
| `0` | 0 |
| конечное число больше нуля | `min(v, 120)` |
| отрицательное, `NaN`, бесконечность, не-число | 12 |

Альтернативы: `options.swimSpeed ?? 12` — отвергнута, потому что `??` пропускает дальше любую строку, включая пустую; проверка на «ложь» вроде `|| 12` — отвергнута принципиально, она превратила бы `0` в `12` и сделала бы статичную утку недостижимой, то есть самый важный сценарий ломался бы молча.

Строки принимаются не из снисходительности: подстановка `{env:...}` и `{file:...}` в конфигурации работает только внутри JSON-строк, а числового поля без кавычек в JSON не существует, поэтому значение из переменной окружения приходит именно строкой. При этом незаданная переменная заменяется пустой строкой, а `Number("")` равно нулю — поэтому пустая строка разбирается как отсутствие, а не как ноль. Это решение проверяется отдельными тестами на каждую строку таблицы.

Значение сверх 120 ограничивается, потому что на максимальной скорости переход через полосу занимает доли секунды и анимация теряет смысл. Снизу не ограничивается намеренно: очень малые значения выглядят как медленное плавание, и это выраженное намерение, а не ошибка.

### Компонент остаётся чистой функцией пропсов

`Ducksay` получает `primary`, `swimSpeed`, `renderer` и `running` пропсами, а `setup` передаёт их из своего замыкания, где доступен настоящий контекст хоста. `usePlugin()` внутри компонента, отображаемого слотом, использовать нельзя: вне хоста он бросает `PluginContextProvider is missing`, а тесты рендерят раздел именно без хоста.

Следствие для тестов: `test/section.test.tsx` ничего не знает про `context.options` и подсовывает число и рендерер напрямую, а весь разбор конфигурации проверяется отдельно без рендера.

### Покадровая проверка на управляемых часах

`testRender` получает `ManualClock`; тест двигает время через `advance`, вызывает `renderOnce` — он проводит ровно один полный кадр вместе с кадрами анимации — и читает результат через `captureCharFrame()`. Сравнение соседних кадров даёт проверку движения без гонок с реальным временем. Требование об освобождении кадров проверяется состоянием планировщика рендерера, а не косвенно.

Нарисованный вручную спрайт проверяется отдельно: TUI запускается в сессии tmux фиксированного размера, кадр снимается командой `tmux capture-pane` — тот же приём, что в прошлом change. Тест проверяет структуру арта, глаза проверяют рисунок.

## Risks / Trade-offs

- **[Отраслеженный спрайт выглядит не так, как задумано]** → тест отношения зеркала ловит правку одного спрайта в одиночку, но не ловит неудачный рисунок; результат проверяется снятием кадра в tmux. Это осознанное разделение: отношение проверяется машинно, рисунок глазами.
- **[Реактивность `data.session.status()` неизвестна]** → источником истины служит store из `storage.memory`; обращение к `data.session.status()` используется только как значение по умолчанию при монтировании, и его отсутствие реактивности ничего не ломает.
- **[Неизвестно, держит ли хост рендерер живым во время хода]** → на цену влияет только, на поведение нет; если хост уже держит кадры, плавающая утка бесплатна, если нет — её ценой является удержание цикла до конца хода. Записано как риск, а не как утверждение.
- **[Докировка удерживает рендерер после конца ответа]** → при скорости по умолчанию это от 0 до примерно 2.4 с (полоса около 29 колонок, 12 колонок в секунду), в среднем около 1.2 с. Принято осознанно: эффект «доплыла домой» этого стоит, а `swimSpeed: 0` остаётся выходом для тех, кому анимация не нужна.
- **[Очень малая скорость удерживает рендерер очень долго]** → например, `swimSpeed: 1` растягивает переход через полосу примерно на полминуты. Снизу не ограничивается, чтобы не мешать выраженному намерению; в справке по опции указано, что значения меньше единицы дают очень долгое плавание.
- **[Панель скрыта или терминал слишком узок]** → компонент размонтируется, `onCleanup` отменяет кадр; требование о прекращении цикла закрыто тестом на размонтирование во время движения.
- **[Полоса уже арта]** → предел положения ограничивается снизу нулём, утка остаётся у левого края и не перемещается, плагин продолжает работать.
- **[Требование «Арт выровнен по левому краю» ослаблено]** → постоянное выравнивание больше не выполняется, поэтому требование изменено явно, а не обойдено молча; остальные требования capability не затронуты.

## Migration Plan

Пользователь обновляет пакет и перезапускает OpenCode. Миграции данных нет.

```json
{
  "plugins": ["opencode-ducksay"]
}
```

Запись остаётся рабочей без изменений: новая скорость имеет значение по умолчанию, а анимация включается сама. Чтобы задать скорость, запись переводится в объектную форму:

```json
{
  "plugins": [{ "package": "opencode-ducksay", "options": { "swimSpeed": 20 } }]
}
```

Откат: закрепить версию `opencode-ducksay@1.0.0` или отключить плагин префиксом `-`. Состояние проекта не пишется, откатывать нечего.

## Open Questions

- Применяется ли подстановка `{env:...}` и `{file:...}` именно к `cli.json`. Документация описывает её для конфигурационных файлов в общем виде, отдельного подтверждения для файла CLI нет. Решение не меняется в любом случае: числовые строки принимаются в любом случае, вопрос касается только того, как сформулировать примечание в справке по опции.
