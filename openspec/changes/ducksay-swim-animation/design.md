# Design

## Context

См. `proposal.md` — Why. Здесь только то, что определяет технический выбор.

Наблюдённые факты об API хоста, на которые опирается дизайн (проверены по типам `@opencode/plugin@2.0.28` и по исходникам `@opentui/core@0.6.4`):

- Слот `sidebar.content` передаёт в `render` реактивный `sessionID`; вход слота не содержит ширины (в отличие от `session.panel`, где есть `width`).
- `data.session.status(id)` отдаёт `"idle" | "running"`, но документация CLI-плагинов помечает реактивность только у `ui.model.current()` и `ui.tabs.list()`. Для `data.*` такой пометки нет.
- `storage.memory(key, { initial })` возвращает `Store<Value>` из `solid-js/store` — чтение его полей в вычислении Solid реактивно по определению; значение переживает hot-reload плагина и не переживает перезапуск TUI.
- `PluginOptions` — это `Record<string, any>`: хост не проверяет ни типы, ни диапазоны опций.
- Рендерер хоста работает не постоянно, а по запросу. В его прототипе есть `requestLive`, `dropLive`, `requestRender`, `setFrameCallback`, `auto`, `pause` — и **нет** `requestAnimationFrame`: версия OpenTUI в хосте (2.0.17) старше той, что стоит в `node_modules` проекта (0.6.4).
- `renderer.clock` — тот же `Clock`, который принимает `CliRendererConfig`, поэтому `testRender` позволяет подставить `ManualClock`; у таймеров этого часа есть `pendingTimerCount`. Глобальные `setInterval`/`clearInterval` часа не касаются: они остаются настоящими.
- Bun, которым OpenCode транспилирует исходники плагина, не ставит `tsconfig` из проекта, поэтому `solid-js` под его условиями резолвится в `dist/server.js` — SSR-сборку, где эффекты выполняются один раз. Плагин импортирует `solid-js/dist/solid.js`, как это делает сам `@opentui/solid`, и `tsconfig.json` отображает этот путь на типы пакета.
- У `Renderable` есть геттер `width`, а у JSX-элементов — проп `ref`, поэтому ширину своей области можно измерить самому.
- Серверное событие `session.status` несёт `{ sessionID, status }`, где `SessionStatus` — это `idle`, `busy` или `retry`, но хост его не публикует: за ход приходят `session.execution.*`, `session.step.*`, `session.text.*`, `session.tool.*`. Подтверждено логом живого TUI.
- JSX-трансформер Bun выдаёт для `<T prop={value}/>` статический объект, а не геттеры: значение пропса вычисляется один раз. Проверено на живом TUI — значение в разметке не меняется при изменении сигнала, тогда как эффекты перезапускаются.

Текущий код: `src/duck.ts` (одна константа `DUCK` из трёх строк шириной 4, 8, 8), `src/tui.tsx` (компонент `Ducksay` как чистая функция пропсов + `Plugin.define`, регистрирующий `append: "sidebar.content"`). Существующие тесты рендерят раздел через `testRender` без хоста OpenCode и читают кадр через `captureCharFrame()`. Под тесты, которым нужен рендерер, компонент монтируется через `render(node, renderer)` из `@opentui/solid` поверх `createTestRenderer`: рендерер должен существовать **до** монтирования, иначе его нельзя передать пропсом.

## Goals / Non-Goals

**Goals:**
- Утка перемещается по полосе панели весь ход сессии, разворачивается у краёв и останавливается у края носом к центру.
- Плагин читает скорость из опции, разбирает её значение по единым правилам и не падает на мусоре.
- Кадры рендерера занимаются только на время анимации и освобождаются во всех остальных состояниях.
- Поведение проверяется автоматическими тестами, а нарисованный вручную спрайт — дополнительно глазами в живом TUI.
- Раздел остаётся чистой функцией пропсов, чтобы его можно было тестировать без хоста.

**Non-Goals:**
- Новый слот, новая панель, другой раздел или другая его позиция: раздел `Ducksay` остаётся последним в `sidebar.content`.
- Отдельная настройка скорости для докировки: сегодня её нет, и появление второй опции должно быть аддитивным, а не заменой `swimSpeed`.
- След воды, звук, наклон утки, вертикальное покачивание, реакция на конкретные типы инструментов.
- Сохранение позиции утки между перезапусками: поза после запуска определена спецификацией и не зависит от прошлого.
- Настройки, зависящие от сессии или проекта: одна глобальная скорость, потому что `cli.json` — глобальный файл, и всё остальное в плагине тоже глобальное.
- Требования о заголовке, порядке разделов и непереносе строк арта не меняются.

## Decisions

### Момент старта и конца плавания — события исполнения хода

Плавание привязано к `session.execution.started` и `session.execution.succeeded/failed/interrupted`: ход начался — плывём, ход закончился — докируем.

Планировалось тоньше: событие `session.status` с состояниями `idle|busy|retry`. На живом TUI выяснилось, что хост его не публикует — в потоке событий хода есть `session.execution.*` и `session.text.*`, а `session.status` не приходит ни разу. Тип есть в клиентском SDK, но сервер его не шлёт, поэтому опереться на него нельзя.

Подписка на `session.status` и `session.idle` оставлена вместе с `session.execution.*`: на хосте, который их публикует, повторная попытка после ошибки авторизации будет держать утку в движении, а пришедшее позже событие статуса просто перезапишет последнее событие исполнения. Пока таких событий нет, они не мешают.

Альтернативы, отвергнутые по-прежнему: `session.text.delta` (только поток токенов) — утка замирала бы на время вызова инструмента и ожидания прав, и это читалось бы как зависание; «окно от промпта до первого ответа» — хрупко и на глаз неотличимо от выбранного.

### Подписку держит сам раздел, а не `setup`

Раздел подписывается на события сам и держит состояние в своём сигнале; `setup` передаёт ему `data` и `sessionID`. Изначально мост строился через `storage.memory`: подписка в `setup`, состояние в store, чтение store в компоненте. Отвергнуто по двум причинам: store принадлежит Solid хоста, а компонент импортирует свою копию Solid, и пересечение реактивности между копиями ничем не гарантировано; и store для этого не нужен — раздел живёт ровно одну сессию.

`data.session.status(sessionID)` остаётся как начальное значение: панель может открыться посреди хода, когда ни одного события ещё не было.

События фильтруются по `sessionID`: они приходят по всем сессиям, и без фильтра утка панели дёргалась бы от фоновой вкладки.

### JSX в плагине не реактивен — строки рисуются императивно

OpenCode транспилирует исходники плагина через Bun, а его JSX-трансформер не знает про Solid: `content={line()}` вычисляется один раз, при создании элемента, и остаётся замороженным навсегда. Проверено на живом TUI: значение в разметке не меняется, тогда как сигналы и эффекты работают полностью.

Поэтому три строки арта рендерятся пустыми `<text>`, а цикл записи их содержимого присваивает `content` напрямую. Заголовок остаётся статической разметкой.

Отсюда форма пропсов: `isRunning` — функция, а не булево значение, потому что значение пропса замораживается; `sessionID` читается один раз по той же причине; а рендерер слота не читает реактивное состояние вовсе — иначе хост пересоздавал бы компонент на каждом событии сессии и терял бы позицию утки, то есть докировка стала бы невозможна.

Альтернатива: полагаться на `Show` или `For` — они реактивны, потому что читают пропсы внутри своих вычислений, но весь динамический текст всё равно пришлось бы рисовать императивно, так что выигрыша нет.

### Кадры — таймер раздела и один `requestRender` на тик

Раздел запускает интервал на 33 мс, двигает утку и просит у рендерера кадр через `requestRender()`.

Планировалось иначе: `renderer.requestAnimationFrame` с перерегистрацией колбэка в себе, что держит счётчик `live` и даёт плавный цикл. На живом TUI выяснилось, что у рендерера хоста этого метода нет: в его прототипе есть `requestLive`, `dropLive`, `requestRender`, `setFrameCallback`, а `requestAnimationFrame` отсутствует — версия OpenTUI в хосте старше той, что стоит в `node_modules` проекта.

У интервала плюс `requestRender` есть и побочная выгода: плагин никогда не берёт живую ссылку на рендерер, поэтому не держит его включённым между тиками и не обязан ничего балансировать вручную. Требование «анимация не оставляет фоновой работы» выполняется тем, что ссылок не берётся вовсе.

Тик после остановки — no-op: таймер снимается при смене режима, но уже начавшийся тик всё равно выполняется, а двигать покоящуюся уточку нельзя. Остановка в режиме `dock` при этом нормализует позу через `park()`, чтобы нос смотрел в середину полосы при любой причине остановки.

Альтернативы: `setFrameCallback` — сеттер один, вызов из плагина затёр бы колбэк хоста; `requestLive` плюс интервал — держит рендерер включённым постоянно, что дороже и сложнее в отладке.

Расписание передаётся пропсом `schedule` со значением по умолчанию из глобального `setInterval`: тест подставляет часы рендерера, чтобы шаг анимации не зависел от реального времени.

### Ширина полосы измеряется у себя

Полоса — ширина контейнера раздела, а предел положения — `max(0, ширина − ширина арта)`. Ширина читается у renderable, полученного через `ref` на корневой `<box>`, на каждом шаге.

Альтернатива: зашить константу `SESSION_SIDEBAR_WIDTH = 42` и производную от неё ширину 37. Отвергнута по причине, уже зафиксированной в прошлом change: это жёсткая связь плагина с внутренней константой чужого проекта, которая ломается при изменении раскладки. Проверка — `test/section.test.tsx` уже рендерит при ширине 42, то есть поведение на реальной ширине панели продолжает проверяться.

### Поза в покое выводится из инварианта «у края носом к центру»

Утка всегда смотрит в сторону движения, а засыпает сразу после разворота у края. Из этого следует всё остальное: старт — левый край носом вправо; докировка — до ближайшего края и разворот; альтернативное правило «возвращаться в ноль» не понадобилось бы вовсе.

Альтернатива: после конца хода возвращать утку к левому краю — отвергнута: это второй, независимый способ завершения анимации, своя фаза и свои тесты, при выигрыше в одну колонку.

### Второй спрайт — зеркальное отражение первого, а не нарисованный отдельно

Нос вправо получается отражением исходного спрайта по горизонтали: строки разворачиваются, а глифы, у которых есть зеркальная пара, заменяются на неё — `<`↔`>`, `(`↔`)`, `/`↔`\`; остальные символы, включая пробелы, остаются как есть.

Простой разворота строк недостаточно: `<` переехал бы в конец строки, но раскрылся бы в ту же сторону, то есть клюв смотрел бы влево, и уточка получилась бы с хвостом слева и головой справа. Именно замена глифов превращает перестановку в отражение.

Исходные строки выравниваются по общей ширине блока до отражения. Без этого у отражения нет пары: строка `  __` длиной 4 не имеет соответствия, и «зеркало» перестаёт быть определённым. Ширина блока становится свойством арта, а не результатом подгонки, и предел положения перестаёт зависеть от конкретного глифа.

Альтернативы: нарисовать второй спрайт вручную и полагаться на глаз — отвергнута: результат похож на зеркало только приблизительно, а расхождение заметно именно в момент разворота, то есть в движении; зеркалировать на уровне ячеек — в OpenTUI недоступно; вычислять второй спрайт из первого в рантайме — отвергнута: арт остаётся данными, которые читаются и правятся как данные, а неизменность отношения обеспечивается тестом; держать в арте только нос вправо и разворачивать его — отвергнута тем же, что перевёрнутый нос влево смотрит вправо, то есть нужен всё равно исходный.

Отношение зеркала проверяется тестом: каждая строка правого спрайта равна развёрнутой строке левого с заменой парных глифов, а двойное отражение возвращает исходник. Тест не фиксирует сами символы и потому не мешает правке рисунка, но ловит правку одного спрайта в одиночку. Визуально результат проверяется отдельно — снятием кадра в tmux.

### Скорость измеряется колонками в секунду

Скорость переводится во время между колонками как `1000 / swimSpeed`; за каждый тик к накопленному времени добавляется фиксированные `TICK_MS`, и колонка проходится, когда накопленное время достигает этого шага. Единица выбрана потому, что это единственная величина, которую видно глазом, и она не зависит ни от частоты тиков, ни от ширины панели.

Альтернатива: «колонок за фиксированный такт 80 мс» — отвергнута: число в конфиге оказывается привязанным к внутренней константе, которую нельзя поменять незаметно для пользователя; строковые режимы вроде `slow`/`fast` — отвергнуты: три состояния вместо числа, при этом точная настройка невозможна.

### Нулевая скорость выключает анимацию, а не её темп

`swimSpeed: 0` проходит мимо разбора как корректное значение и выключает анимацию: раздел не заводит таймер вовсе, уточка стоит у левого края носом вправо. Это осмысленное значение, а не отключение плагина, потому что раздел с заголовком и уточкой остаётся на месте.

Нулевая скорость полностью воспроизводит поведение 1.0.0 и не добавляет к нему ничего: таймера нет, перерисовок нет.

### Разбор значения — чистая функция с явной проверкой отсутствия

`resolveSwimSpeed(options)` живёт отдельно от компонента и возвращает число:

| вход | результат |
| --- | --- |
| опции или ключа нет, `null` | 12 |
| строка, у которой `trim()` пуст | 12 |
| строка с числом | это число |
| `0` | 0 |
| конечное число больше нуля | `min(v, 120)` |
| отрицательное, `NaN`, бесконечность, не-число | 12 |

Альтернативы: `options.swimSpeed ?? 12` — отвергнута, потому что `??` пропускает дальше любую строку, включая пустую; проверка на «ложь» вроде `|| 12` — отвергнута принципиально, она превратила бы `0` в `12` и сделала бы статичную утку недостижимой, то есть самый важный сценарий ломался бы молча.

Строки с числом принимаются. Проверено, что подстановка `{env:...}` и `{file:...}` к `cli.json` **не применяется**: ссылка приходит в плагин литералом, то есть не-числом, и разбирается в значение по умолчанию. Причина принятия строк поэтому простая: кавычки вокруг числа — обычная опечатка, и молча взять вместо просимого 30 значение 12 хуже, чем принять написанное. Пустая строка при этом остаётся «unset», а не нулём, потому что `Number("")` — это `0`: пустое поле в конфиге не должно читаться как команда «утка не двигается». Каждая строка таблицы закрыта отдельным тестом.

Значение сверх 120 ограничивается, потому что на максимальной скорости переход через полосу занимает доли секунды и анимация теряет смысл. Снизу не ограничивается намеренно: очень малые значения выглядят как медленное плавание, и это выраженное намерение, а не ошибка.

### Компонент остаётся чистой функцией пропсов

`Ducksay` получает `primary`, `swimSpeed`, `renderer`, `data`, `sessionID` и `isRunning` пропсами, а `setup` передаёт их из своего замыкания, где доступен настоящий контекст хоста; `schedule` и `sprites` существуют только для тестов и по умолчанию не меняют поведение. `usePlugin()` внутри компонента, отображаемого слотом, использовать нельзя: вне хоста он бросает `PluginContextProvider is missing`, а тесты рендерят раздел именно без хоста.

Следствие для тестов: `test/section.test.tsx` ничего не знает про `context.options` и подсовывает число и рендерер напрямую, а весь разбор конфигурации проверяется отдельно без рендера.

### Покадровая проверка на управляемых часах

`createTestRenderer` получает `ManualClock`, а раздел запускает свой таймер на часах — через пропс `schedule` или подменой глобальных таймеров там, где монтируется слот плагина. Тест двигает время через `advance` и читает результат через `captureCharFrame()`. Сравнение соседних кадров даёт проверку движения без гонок с реальным временем; освобождение таймера проверяется счётчиком активных расписаний, а не состоянием планировщика рендерера, потому что живую ссылку плагин больше не берёт.

Шаг времени внутри тика фиксирован и не берётся у часов: интервал идёт по настоящему времени, и добавление `TICK_MS` за тик отличается от реального интервала на доли процента — для декоративной анимации это не имеет значения, зато тест становится полностью детерминированным.

Размонтирование в тестах не проверяется: `render()` не отдаёт функцию очистки, а под условиями Bun `@opentui/solid` разрешается в SSR-сборку Solid, где очистка владельца не выполняется. Тот же путь закрывается проверкой живым TUI: при скрытии панели раздел пропадает и работа продолжается.

Спрайт проверяется отдельно: TUI запускается в сессии tmux фиксированного размера, кадр снимается командой `tmux capture-pane` — тот же приём, что в прошлом change. Тест проверяет структуру арта, глаза проверяют рисунок.

## Risks / Trade-offs

- **[Отраслеженный спрайт выглядит не так, как задумано]** → тест отношения зеркала ловит правку одного спрайта в одиночку, но не ловит неудачный рисунок; результат проверяется снятием кадра в tmux. Это осознанное разделение: отношение проверяется машинно, рисунок глазами.
- **[Хост не публикует `session.status`]** → плавание ведёт `session.execution.started/succeeded/failed/interrupted`, которые приходят всегда; на хосте, где статус появится, он перезапишет последнее событие исполнения и удержит утку во время повторной попытки. Риск в том, что у другого хоста может не оказаться и `session.execution.*` — тогда утка просто не плывёт, а не ломается.
- **[Две копии Solid — у хоста и у плагина]** → всё реактивное состояние раздела живёт в его собственном сигнале, а чтение чужого store не используется нигде; единственная зависимость от чужой реактивности — `data.on`, которая доставляет события обычным колбэком.
- **[Цена анимации — перерисовка панели на каждом тике]** → тик идёт 30 раз в секунду и просит кадр после каждой перерисовки строк; чем длиннее ответ, тем больше работы у хоста, хотя панель узкая. Смягчается тем, что живая ссылка на рендерер не берётся: между тиками хост решает сам, нужен ли ему кадр.
- **[Докировка держит таймер после конца ответа]** → при скорости по умолчанию это от 0 до примерно 2.4 с (полоса около 29 колонок, 12 колонок в секунду), в среднем около 1.2 с. Принято осознанно: эффект «доплыла домой» этого стоит, а `swimSpeed: 0` остаётся выходом для тех, кому анимация не нужна.
- **[Очень малая скорость держит таймер очень долго]** → например, `swimSpeed: 1` растягивает переход через полосу примерно на полминуты. Снизу не ограничивается, чтобы не мешать выраженному намерению; в справке по опции указано, что значения меньше единицы дают очень долгое плавание.
- **[Панель скрыта или терминал слишком узок]** → компонент размонтируется, `onCleanup` снимает таймер; проверено на живом TUI в узком терминале: раздел пропадает, работа продолжается, ошибок нет. В автоматическом тесте путь размонтирования недоступен (см. решение о проверке), поэтому страхует сам тик: он выходит немедленно, если режим стал `rest`.
- **[Версия OpenTUI в хосте может отстать ещё сильнее]** → плагин использует только `requestRender` и глобальный `setInterval`; и то и другое — базовые API, которые дешевле всего убрать последними. `setFrameCallback` не используется намеренно.
- **[Полоса уже арта]** → предел положения ограничивается снизу нулём, утка остаётся у левого края и не перемещается, плагин продолжает работать.
- **[Требование «Арт выровнен по левому краю» ослаблено]** → постоянное выравнивание больше не выполняется, поэтому требование изменено явно, а не обойдено молча; остальные требования capability не затронуты.
- **[Горячая перезагрузка не пересобирает уже отрисованный раздел]** → перечитывание плагина перерисовывает арт, но компонент на экране остаётся прежним, и анимация в открытой панели продолжает вести себя по-старому. Наблюдено на живом TUI: правка арта видна сразу, правка анимации — только после перезапуска. Поэтому позиция и режим утки намеренно не хранятся в `storage.memory`: при перезагрузке всё равно нужен перезапуск, а состояние, переживающее hot-reload, только обещало бы сохранить позу у панели, которой скоро не будет. Требование в README и README.ru описывает перезапуск как часть рабочего цикла.
- **[Глобальная настройка `animations` OpenCode не влияет на утку]** → у `cli.json` есть `animations`, выключающая анимации интерфейса, но SDK плагина её не отдаёт: `Context` содержит только опции самого плагина, а настроек хоста среди них нет. Уважение к ней реализовать нечем, поэтому единственный выключатель — `swimSpeed: 0`, и это указано в справке по опции. Требование не добавлено: подключение к чужой настройке без API сделало бы его невыполнимым.

## Migration Plan

Пользователь обновляет пакет и перезапускает OpenCode. Миграции данных нет.

```json
{
  "plugins": ["opencode-ducksay"]
}
```

Запись остаётся рабочей без изменений: новая скорость имеет значение по умолчанию, а анимация включается сама. Чтобы задать скорость, запись переводится в объектную форму:

```json
{
  "plugins": [{ "package": "opencode-ducksay", "options": { "swimSpeed": 20 } }]
}
```

Откат: закрепить версию `opencode-ducksay@1.0.0` или отключить плагин префиксом `-`. Состояние проекта не пишется, откатывать нечего.

Открытых вопросов не осталось: единственный — применяется ли подстановка `{env:...}` к `cli.json` — закрыт проверкой на живом TUI, см. решение о разборе значения.
